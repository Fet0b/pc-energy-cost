# pc-energy-cost — requisitos para plano revisado (sem implementação)

## Requisitos expressos do usuário
Programa completo standalone de código comum: calcula em BRL energia atribuível a um PC ligado por duração planejada; não é agente e não usa LLM, Hermes ou nuvem de IA no runtime. DDD + Spec-Driven Development pelo plugin instalado, plano revisado antes de implementar. Autotarifa oficial, iniciar São Paulo, expansão de regiões brasileiras e persistência cidade↔distribuidora. Telemetria Windows por provider real e Linux quando disponível. Proxmox somente fronteira de extensão, implementação adiada. Interface instalável/usável, exportação, documentação em português e testes/reais integrações na fase de implementação. Sem publicação/GitHub remoto/deploy/commit nesta fase. Produzir artefatos de planejamento, não stubs de programa.

## Defaults PROVISÓRIOS, não exigências já aprovadas
Python 3.11+ CLI com saída humana em português e JSON versionado como primeira UI utilizável, SQLite para preferências/mapeamentos/cache indexado, stdlib onde sensato. São Paulo significa CAPITAL, IBGE 3550308, Enel Distribuição São Paulo; perfil inicial residencial B1 convencional, sem tarifa social/branca. Não representa todo o estado. Catálogo inicial explicitamente parcial com capital verificada; resolvedor extensível, sem inventar cobertura nacional completa. TTL sugerido 24h para refresh, offline stale somente opt-in com idade/validade explícitas. Não perguntar preferências de baixo impacto agora: registrar defaults para aprovação humana junto ao plano.

## Semântica e aceitação essenciais
Custo estimado da energia atribuível, não fatura residencial completa. Energia kWh = W × horas / 1000; MoneyBRL e Watts/Wh/kWh/Duration/UnitRate como value objects Decimal, nunca float de dinheiro, quantização só na apresentação/total com regra explícita (sugestão HALF_UP), entradas com precisão documentada e limites de magnitude. Zero duração/potência é válido e produz zero; negativo/NaN/infinito inválidos. Horas/dias/agendas com timezone America/Sao_Paulo, intervalos não sobrepostos, energia integrada de CSV timestamps/Watts com gaps e duplicatas definidos; energia acumulada não confundir com potência. Datas futuras fora de vigência não inventam tarifa: projeção pela última conhecida só com warning/consentimento explícito, ou tarifa manual; divisão por períodos quando disponíveis, endpoints inclusivos/exclusivos fixados. Testar arredondamento, separador decimal brasileiro/JSON, moeda BRL, agendas, sobreposição e intervalos inválidos.

Tarifa automática: efetivamente acessar CSV ANEEL + dicionário, inspecionar schema real, unidades e linhas atuais/mais recentes disponíveis. Selecionar agente estável (CNPJ/código quando houver, aliases Eletropaulo/Enel SP só verificados), período, grupo/subgrupo B1, residencial normal, convencional, posto, base de aplicação, unidade e demais dimensões reais para evitar duplicidade/subclasse/benefício. TE+TUSD quando ambas em R$/MWh -> somar e dividir 1000; não somar registros de demanda R$/kW nem somar períodos/duplicatas. Capturar fonte, resource ID, resolução, datas vigência e atualização, URL, fetched_at UTC, hash, unidades originais, critérios completos. Cache atômico, bounded downloads/timeouts, validação, erro de schema/HTML inesperado, cache poisoning/stale e rede ausente explícitos. Dataset incompleto/não vigente não deve alegar tarifa de hoje. Não usar tarifa hardcoded inventada.

Tarifa ANEEL básica exclui tributos, bandeiras e encargos fixos salvo fonte/perfil explicitamente inclua. Manual all-in R$/kWh derivado da fatura permite inclusões declaradas; não acrescentar novamente imposto/bandeira já inclusos. Componentes opcionais: energia adicionais R$/kWh e/ou tributo por fórmula com base e gross-up explícitos, ou adiar modelo tributário complexo para manual all-in; nunca pseudoexatidão. Custos fixos de residência não rateados automaticamente ao PC. PSD/PSU potência nominal máxima não é consumo AC real e deve aparecer apenas como cenário explícito, não telemetria.

Mapeamento: pesquisar fonte oficial município/IBGE↔distribuidora, inspecionar cobertura/colunas e múltiplas distribuidoras por município. IBGE identifica município mas sozinho não identifica concessionária; nenhuma relação um-por-estado. Persistir relações muitos-para-muitos com proveniência, intervalo se disponível, confiança e escolha confirmada do usuário distinta da fonte oficial. Ambiguidade pede seleção da distribuidora da conta; sem cobertura retorna unsupported, não chute. Lista oficial Enel confirma capital e 24 municípios, não é catálogo nacional. Procurar ANEEL IndQual Município ou concessão/dados geográficos adequados, sem assumir que indicadores são cadastro exaustivo de concessões.

Telemetria: port MeteringProvider com disponibilidade/escopo (whole_system_ac versus cpu_package/component), amostras/unidades/timestamps e motivo indisponível. Manual average watts e CSV temporal executáveis em qualquer plataforma. Linux RAPL powercap fornece energia CPU/package e possivelmente zonas internas, não tomada PC; delta energy_uj/time, max_energy_range_uj para wrap, monotonic timer, permissão/ausência/reset e múltiplos wraps indetermináveis, sem double-count de zonas aninhadas. Windows Win32_PowerMeter root\CIMV2\power requer hardware/provider suportado, não DLL universal; disponibilidade local Linux não valida Windows. Se API WMI insuficiente, indisponível explícito; nunca zero fabricado nem escalar CPU para PC completo. Wallplug/IPMI/smartplug apenas read-only opcional se provider existente justificado; não instalar drivers/serviços privilegiados. Proxmox apenas futuro adapter/port documentado, sem plugin agora. Não medir watts via PSU rating.

DDD: domínio puro sem HTTP/SQLite/OS/UI; contextos EnergyEstimation, TariffCatalog, LocationSupplierMapping e Metering com application usecases/ports/adapters de infraestrutura/persistência e composition root CLI. Tipos de erro previsíveis e schema JSON; nenhuma dependência de Claude/Hermes em produto. Arquitetura enxuta e testável, sem framework DDD por estética. Checklist de instalação clean wheel/sdist, CLI --help, inputs manuais, CSV, busca tarifa live e offline, export JSON, testes contrato de adapters e arquitetura, Windows real somente quando hardware disponível (não confundir mocks com live). Matriz requisitos↔testes com entradas e saídas esperadas, sem afirmar testes do programa já executados nesta fase.
